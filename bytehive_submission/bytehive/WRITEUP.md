# Technical Write-Up: ByteHive Support Draft Assistant

## 1. Problem framing

ByteHive needs support drafts that are simultaneously:
- **On-tone** (direct, friendly, no corporate boilerplate), and
- **Policy-accurate** (never states a refund/billing/cancellation rule that isn't
  actually true).

The client's own history shows these two requirements pull against each other if
handled naively: prompt-only approaches held neither under drift, and an early
fine-tune that nailed tone lost policy accuracy in the process ("style overfit,
substance lost"). The core design decision in this submission is to **not** ask one
mechanism to do both jobs.

## 2. Architecture: LoRA for tone, RAG for facts

| Requirement | Mechanism | Why |
|---|---|---|
| Brand voice / tone | LoRA fine-tuning on `Qwen2.5-7B-Instruct` | Tone is a *style* property -- consistent phrasing, structure, and register are exactly what parameter-efficient fine-tuning is good at learning from a moderate number of examples. |
| Policy accuracy | Retrieval (FAISS over `data/policies/*.md`) injected into the prompt at both train and inference time | Facts that must never be wrong should not live in model weights, where they're opaque and prone to being "smoothed over" or misremembered during generation. Keeping them in retrieved, human-editable text means: (a) updating a policy is a doc edit, not a retrain, and (b) the model can be trained to say "I answer only from what's retrieved," which is directly checkable. |

This is why "Style Overfit, Substance Lost" happened in ByteHive's earlier attempt:
fine-tuning was almost certainly used to teach the model *both* tone and policy
facts at once. Every additional epoch pushing tone further also reshapes how
confidently the model states things it half-remembers, including things it never
should state. Splitting the two removes that trade-off: the fine-tune's job is
narrowed to "sound like ByteHive, and only speak from the provided context,"
never "know ByteHive's policies from memory."

The **same retriever** (`rag/retriever.py`) is used to build training examples
(`train/prepare_training_data.py`) and to serve the app and evaluation
(`app/model_utils.py`), so the model is never trained on a different shape of
context than it sees in production.

## 3. Base model choice

`Qwen/Qwen2.5-7B-Instruct` -- Apache 2.0 licensed, open weights, no gating, strong
instruction-following for its size, and fits 4-bit QLoRA fine-tuning on a single
16GB GPU. This satisfies the "top-performing, freely available for fine-tuning"
constraint without requiring a paid endpoint or closed license. `finetune_lora.py`
notes `meta-llama/Llama-3.1-8B-Instruct` as a drop-in alternative (same recipe,
gated but free) if a team prefers it.

QLoRA (4-bit base weights + LoRA adapters on attention/MLP projections, rank 16)
rather than full fine-tuning keeps this inside a realistic student-project budget:
a few hundred MB adapter instead of a full 7B-parameter checkpoint, and training
completes on the seed dataset in well under an hour on a single T4/L4-class GPU.

## 4. Data construction

Each training example is a `(ticket, retrieved_policy_context, ideal_reply)`
triple (`data/tickets_dataset.jsonl`, generated by
`data/build_seed_dataset.py`). Construction process:

1. Write a realistic customer ticket across each policy category (refunds,
   billing, cancellations), including edge cases explicitly called out in
   ByteHive's policy docs (outage exception, billing-error exception,
   non-refundable add-ons, chargebacks, mid-cycle upgrade/downgrade timing).
2. Pin the exact policy excerpt(s) that should ground the reply -- copied
   verbatim from `data/policies/*.md`, the same source the retriever indexes,
   so training-time grounding matches what retrieval will actually return.
3. Hand-write the reply to satisfy the tone guide (`data/tone_guide.md`) *and*
   restate only facts present in the pinned context, nothing more.
4. Include a deliberate minority of **"uncertain" examples** where the policy
   docs don't clearly address the question (e.g. nonprofit discounts, verbal
   approvals, currency-conversion questions) with a target reply that flags
   uncertainty and offers to escalate, instead of guessing. This is what
   teaches the "uncertain, not confidently wrong" behavior the client asked for.
5. Include a few "polite but firm no" examples so the model doesn't learn a
   sycophantic yes-bias just because it's optimizing for a friendly tone.

The seed set ships with **38** examples for a runnable end-to-end demo within the
6-day window. For a production-strength submission, the same process should be
repeated to **150-300** examples: draft candidates faster with an LLM, but every
single example must be human-verified against `data/policies/*.md` line-by-line
before inclusion -- this verification step is what prevents training data itself
from introducing hallucinated policy statements. Skipping it would reproduce
exactly the failure mode this project is meant to fix.

## 5. Evaluation methodology

`eval/evaluate.py` runs both the base and fine-tuned model on the same held-out
tickets with identical retrieved context, then scores each reply on two
**independent** axes (never averaged together):

**Tone consistency** -- LLM-as-judge (`eval/judge_prompts.TONE_JUDGE_PROMPT`)
rates directness, friendliness, specificity, absence of boilerplate, and
conciseness on a 1-5 scale each, per ByteHive's tone guide.

**Policy grounding** -- a two-step claim-level check:
1. Extract every discrete factual/policy claim from the reply
   (`CLAIM_EXTRACTION_PROMPT`).
2. For each claim, check it against the retrieved policy context and label it
   `supported`, `unsupported` (hallucination risk), or `contradicted`
   (`GROUNDING_JUDGE_PROMPT`).

This produces a `grounding_rate` (fraction of claims actually supported) and a
`has_hallucination` flag per reply, plus an aggregate `pct_replies_with_hallucination`
in `eval/report/eval_summary.csv` -- so a reply that sounds perfectly on-brand but
invents a refund rule shows up as a *grounding* failure, not hidden inside a good
tone score. This directly targets "No Way to Tell What Changed" and "Style
Overfit, Substance Lost" from the client's failure history: the summary CSV makes
both axes visible side-by-side for base vs. fine-tuned, on the same tickets.

### Known limitation: judge is the base model itself

To stay within a single-model resource budget, the judge in `eval/evaluate.py` is
the same base Qwen2.5-7B-Instruct model (not the fine-tuned adapter, to avoid
obvious self-preference bias, but still the same underlying model family). This
is a real limitation -- self-evaluation can be optimistic or share blind spots
with the model being judged. Recommended upgrades, in order of effort:
1. Spot-check ~15-20% of judge scores by hand (a support team lead, matching the
   client's existing weekly spot-check process) and report agreement rate.
2. Swap the judge for a different model family if a second free API/local model
   is available.
3. Replace the LLM grounding judge with a smaller, purpose-built NLI model
   (e.g. an entailment classifier) for the "supported/unsupported/contradicted"
   step specifically, which is a narrower and more checkable task than open-ended
   tone judging.

## 6. Uncertainty handling in the app

`rag/retriever.py` computes a cosine-similarity threshold
(`UNCERTAINTY_THRESHOLD`) on the top retrieved chunk. If retrieval doesn't clear
that threshold, `app/streamlit_app.py` shows a visible warning banner above both
drafts rather than letting either model's output look more authoritative than the
retrieval actually supports. The fine-tuned model is also trained (via the
"uncertain" examples in the dataset) to write an explicit "I don't have that
confirmed in our policy docs" sentence in these cases, so the signal shows up in
both the retrieval layer and the generated text, not just one.

## 7. Limitations

- **Dataset scale**: 38 seed examples is enough to demonstrate the pipeline and
  produce a directionally meaningful before/after comparison, but is below the
  150-300 examples recommended for a production-ready tone fine-tune; expect the
  base model's raw instruction-following to still show through more than it
  would with the full dataset.
- **Judge bias**: see Section 5 above.
- **Retrieval granularity**: chunking is header-based (one chunk per `##`
  section per policy doc). This works well for ByteHive's current three short
  policy docs but would need smaller/overlapping chunks if policy docs grow much
  longer or denser.
- **No multi-turn context**: the app and training data treat each ticket as a
  single-turn draft. Real tickets sometimes have back-and-forth history; this
  version does not use prior messages in a thread as additional input.
- **English-only**: tone guide and training data assume English-language tickets.
